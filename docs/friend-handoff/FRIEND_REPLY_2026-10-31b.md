# HnS 남은 항목 반영 확인 및 알 처리 원본 복원·도구 보존 최종 요청

`followup-2026-10-31.md`의 수정·조사·검증 결과 확인했어.

텔레키네시스·불사르기 공식 본문, 테스트 기본값 페어리 ON, 팝업 입장 대기는 보고한 방향으로 유지해 줘.

재확인 70은 **알 처리 규칙을 원본 HnS 방식으로 복원**하고, 114는 **도구 보존 처리와 아래에서 확정한 안내 문장 2개를 적용**해 줘.

작업은 네 클라우드 환경에서 진행하고, 내 QA 환경과 메인 한글화 로컬은 건드리지 말아 줘. mGBA 실기는 내가 별도로 진행할게.

## 1. 이번에 완료한 수정 유지

다음 반영 상태는 그대로 유지해 줘.

- **텔레키네시스:** 대상 목적격 조사＋`허공에 띄웠다!`.
- **불사르기:** 보유자·도구 이름＋주격 조사＋`불타 없어졌다!`.
- **89(1):** 테스트 기본값 페어리 ON, OFF 검사는 각 테스트에서 명시.
- **37:** 딜레이 생략 ON에서도 최신 특성·도구 팝업이 들어오는 동안 필요한 최소 대기.
- **34:** 현재 HnS 노가드 × 프리폴 동작 유지, 제외 hunk는 적용하지 않음.
- **82:** `B_OVERWORLD_WEATHER_OVERRIDE GEN_8`과 설명 주석 유지, 별도 설정 이름 추가 없음.

README, 매지컬리프, 엔진 버전, 춤추기, `B_MULTI_HALF_TEAMS FALSE`, 슬라이드 표 축소, Set Ability 취소 방어도 유지해 줘.

37의 장면별 프레임 계측은 자동 계측 결과로 기록할게. 파티·가방 화면 복귀 후 멈춤 여부와 실제 체감은 내 실기 대기야.

과거 2.6%는 이번 수정의 최신 측정값으로 사용하지 말고, 배틀 전체 시간 비율은 미실행으로 남겨 줘.

## 2. 재확인 70(a) — 알 처리 규칙은 원본 HnS 방식으로 복원

개발자 원본 HnS의 보충 처리를 확인한 뒤 결정했어.

**실제로 보충이 필요한 상황에서의 알 처리는 다음 원본 방식으로 되돌려 줘.**

- 박스에 살아 있는 비알 포켓몬이 있으면 파티 0번 칸에 직접 배치.
- 박스에도 없으면 파티 전체를 비우고 꼬렛 Lv1 지급.

이 과정에서 다음 알 소실 가능성도 원본 동작으로 수용할게.

- 박스 포켓몬을 0번 칸에 넣으면서 그 자리에 있던 알이 덮어써짐.
- 꼬렛 지급을 위해 파티를 초기화할 때 남아 있던 알도 사라짐.

따라서 다음 알 보존 처리는 제거해 줘.

- 알을 뒤로 밀어 개체와 순서를 보존하는 처리.
- 파티 제한이 꽉 찼을 때 마지막 알을 PC로 보내는 처리.
- PC까지 꽉 찼다는 이유로 보충을 중단하고 알만 있는 파티로 돌려보내는 처리.

이번 결정은 **원본의 알 소실 가능성까지 알고 선택한 정책 변경**으로 기록해 줘. 원본 개발자의 의도까지 확인된 것으로 표현할 필요는 없어.

PC에 있는 죽은 포켓몬을 지워 자리를 만드는 방식은 추가하지 말아 줘.

## 3. 원본 복원과 별개로 유지할 보호 수정

알 보존 정책을 되돌린다고 다른 보호 수정까지 함께 되돌리지는 말아 줘.

다음은 그대로 유지해 줘.

- **재확인 67:** 미러 패배·기권 등에서 살아 있는 원래 파티가 복구됐을 때 보충으로 덮어쓰지 않는 보호.
- **70(b):** 파트너 배틀의 기절 삭제 면제와 원래 파티 회복.
- **70(b):** 삭제 면제로 기절한 비알 포켓몬이 남아 있다면 보충하지 않는 처리.
- 보충 후 마릿수를 정확히 계산해서 보충 포켓몬도 회복하는 수정.
- 하드 너즐록의 기존 세이브 삭제 규칙.

즉, **보충 대상인지 판단하는 보호는 유지하고, 보충하기로 한 뒤의 알 처리만 원본 방식으로 복원**해 줘.

`338a5ebd`에는 여러 수정이 함께 있으므로 커밋 전체를 단순 revert하지 말고 해당 부분만 구분해서 수정해 줘.

## 4. 70의 추가 복구 설계는 진행하지 않음

이번 원본 복원 결정에 따라 다음 작업은 진행하지 않아도 돼.

- PC 종료·센터 회복 때 추가 보충 검사.
- PC 포화 예외를 위한 별도 복구 흐름.
- 이를 위한 야생·시선·대본 배틀 진입 차단.
- 알만 남은 상태의 복구 안내 문장.

관련 문서에는 **알 보존 정책을 원본으로 복원하기로 하여 추가 설계를 진행하지 않음**으로 정리해 줘.

현재 보고된 알 출전 현상은 기록을 지우지 말고, 알 보존·보충 중단 상태에서 확인한 문제라는 조건을 남겨 줘. 이번 복원 후 일반적인 너즐록 패배 경로에서 같은 상태가 남는지 확인해 줘.

다른 경로에서 별개 문제가 발견되면 따로 보고하고, 이번 요청을 이유로 배틀 진입 처리 전체를 확대 수정하지 말아 줘.

### 70 관련 검증

다음을 확인해 줘.

- 노말·이지 각각 박스 생존 후보 있음·없음.
- 알이 없는 파티와 알이 남아 있는 파티.
- 후보가 있으면 0번 칸 직접 보충.
- 후보가 없으면 파티 초기화 후 꼬렛 Lv1 지급.
- 보충 뒤 마릿수와 회복 상태.
- PC 포화 여부 때문에 보충이 중단되지 않는지.
- 미러 원래 파티 보호와 파트너 배틀 삭제 면제·덮어쓰기 방지 유지.
- 하드 너즐록 기존 처리 유지.

알 보존을 기대하던 테스트는 이번 결정에 맞춰 기대값이나 전제를 갱신하고 변경 이유를 남겨 줘. 실제 동작을 확인하지 않고 테스트만 삭제해 결과를 맞추지는 말아 줘.

## 5. 재확인 114 — 도구 보존 처리 진행

**가방 추가 실패 시 PC로 보내고, 가방과 PC가 모두 수용할 수 없으면 훔치기를 막는 방향**으로 진행해 줘.

기준 동작은 다음과 같아.

- 기술 피해는 기존대로 처리.
- 도구를 보관할 수 없으면 상대가 계속 지님.
- 훔치기를 막았는데 성공 문장이 나오지 않음.
- 정상적으로 훔친 뒤 포획하면 지금처럼 포획 개체에게 도구가 돌아감.
- 도주·KO 등으로 끝나면 가방, 실패하면 PC 순서로 지급.
- 같은 도구가 복제되거나 사라지지 않음.

기존 가방·PC의 슬롯·수량 제한과 세이브 구조는 변경하지 말아 줘.

### 5-1. 예약 용량 계산

대기 중인 도구의 총개수만 세지 말고 실제 수용 규칙에 맞춰 계산해 줘.

- 도구별 가방 주머니.
- 같은 도구의 스택 잔량.
- 서로 다른 도구가 차지하는 슬롯.
- PC의 같은 도구 스택과 빈 슬롯.
- 같은 배틀에서 이미 지급 대기 중인 도구.
- 포획으로 해당 도구가 포획 개체에게 돌아갈 때의 예약 해제.

여러 예약이 같은 마지막 자리를 중복으로 사용하는 상황도 막아 줘.

### 5-2. 최종 지급 실패 처리

사전 검사로 종료 시 지급 성공이 보장되는지 코드와 테스트로 확인해 줘.

**실제 추가 함수가 실패했는데 대기 표시만 지워 도구가 사라지는 처리는 남기지 말아 줘.**

현재 구조에서 무손실을 보장할 수 없는 경로가 발견되면, 세이브 구조나 도구 귀속을 임의로 바꾸지 말고 해당 경로의 추가 설계를 알려 줘.

미해결 경로를 남긴 채 114 전체를 해결 완료로 닫지는 말아 줘.

## 6. 재확인 114 — 안내 문장 2개 확정

안내 문장은 다음 두 가지로 적용해 줘.

### 6-1. PC로 보냈을 때

```text
{도구 이름}을/를
PC로 보냈다!
```

실제 출력 경로에 맞는 기존 변수·조사 토큰을 사용해 줘. 배틀 종료 시점에 오래된 버퍼를 읽지 말고, 실제 지급 대상 도구 이름을 준비해 줘.

### 6-2. 공간 부족으로 훔치지 못했을 때

```text
도구가 가득 차서
빼앗을 수 없다!
```

문장과 줄바꿈은 위 내용으로 확정할게.

두 안내는 **공식 표현을 참고해 확정한 HnS 신규 기능용 문장**으로 기록해 줘. 공식 게임의 동일한 상황에서 나오는 문장을 그대로 이식한 것으로 기록하지는 말아 줘.

### 6-3. 출력 조건

- 공간 부족으로 훔치기를 막으면 기존 성공 문장을 출력하지 않음.
- 차단 안내가 공격 자체의 실패로 처리되지 않음.
- 피해·피격·기존 추가 효과의 흐름은 보존.
- PC 이동 안내는 실제 PC 추가가 성공한 경우에만 출력.
- 가방으로 정상 지급한 경우에는 PC 이동 안내를 출력하지 않음.
- 포획 개체에게 도구가 돌아간 경우에도 PC 이동 안내를 출력하지 않음.
- 여러 도구를 PC로 보낼 때 이름과 안내 순서가 섞이지 않음.

문장 폭과 줄바꿈은 실제 사용하는 창 기준으로 측정해 줘.

## 7. 재확인 114 검증

다음 조건을 구분해서 확인해 줘.

- 가방 여유.
- 가방 포화·PC 여유.
- 가방·PC 모두 포화.
- 같은 도구를 여러 번 훔치는 경우.
- 서로 다른 도구가 마지막 슬롯을 경쟁하는 경우.
- 같은 스택에 들어가는 경우와 스택 상한에 걸리는 경우.
- 지급 대기 중인 도구가 있는 상태에서 추가 훔치기.
- 포획에 따른 예약 해제.
- 포획·도주·KO·패배 등 종료 경로.
- 공간 부족으로 차단됐을 때 상대 도구 유지·기술 피해 유지.
- PC 이동·차단 안내의 출력 조건, 도구 이름·조사·줄바꿈.

가방·PC·플레이어 포켓몬·포획 개체의 도구 귀속과 수량을 전후 비교해 줘.

기존 트릭·플레이어 도구 복구·다른 도구 이동 경로도 필요한 범위에서 회귀 확인해 줘.

## 8. 검증과 다음 보고

현재 받은 실기용 ROM 기준은 다음으로 기록했어.

- 코드: `80cd01c1`
- SHA1: `2c1a99accbcfe8d74a4be75053847ba266e1a9f1`
- 사용 용량: 32,607,284 B
- 파일 크기: 33,554,432 B
- 빌드: 클라우드 `make hns -j8`, GCC 13.2.1
- 포함: 공식 본문 2개와 37 팝업 입장 대기.
- 89(1)은 테스트 환경 변경이며 게임 ROM 동작 변경은 아님.

이번 **70(a) 원본 복원과 114 도구 보존 수정은 독립적인 변경**이므로 커밋과 검증 결과를 구분해 줘.

다음 보고에는 아래 내용을 포함해 줘.

1. **70(a):** 원본으로 되돌린 부분과 유지한 보호 수정, 알이 있는 경우를 포함한 검증 결과.
2. **70 추가 설계:** 원본 복원 결정에 따라 진행하지 않는 것으로 정리한 항목.
3. **114:** 실제 변경 코드·커밋, 용량 예약 방식, 확정한 안내 문장 2개의 적용 결과, 자동 검사와 남은 예외.
4. **ROM:** 기준 커밋·SHA1·사용 용량·포함 변경·빌드 환경.

네 작업환경에서 관련 자동 검사·전체 테스트·한글 회귀·세이브 정적 비교를 진행해 줘.

테스트 이름 변경과 실제 PASS 증가를 구분하고, 영문 문장 비교에서 멈춘 테스트는 그 뒤 장면이 미검증이라는 기록을 유지해 줘.

실행하지 않은 검사는 PASS로 처리하지 말아 줘. 실제 팝업 템포, 안내 문장 화면, 패배 후 필드 복귀와 도구 지급 화면 등은 내가 QA 환경에서 확인하겠어.

가로챈 멀리짖기 assert와 막힌 쥬얼 문장 문제, 기존 실기 대기 항목은 그대로 보존해 줘. 이번 작업을 이유로 메가 특성·기존 한글 텍스트·다른 HnS 고유 규칙까지 변경하지 말아 줘.
