# HNS 한글화 세션 워크플로우

## 새 세션 시작

같은 HNS 폴더를 작업 공간으로 열면 루트 `AGENTS.md`가 작업의 진입점이 된다. 다른 도구가 이 파일을 자동으로 읽지 않는 경우 아래 문장을 직접 전달한다.

```text
이 저장소의 AGENTS.md와 docs/localization/{STATUS,WORKFLOW,SESSION_LOG}.md를 읽고,
실제 작업 트리와 대조한 뒤 이어서 작업해줘.
이전 변경은 보존하고, 완료된 이식 작업은 반복하지 마.
이번 작업: [예: 옵션 메뉴의 남은 영문과 한글 표시 문제 수정]
작업을 마치거나 중단하기 전에 인수인계 문서도 갱신해줘.
```

`이번 작업`이 없다면 STATUS의 명시적인 진행 중 작업을 이어간다. 진행 중 작업이 없고 후보만 있다면 사용자에게 작업 대상을 확인한다. 후보 목록 자체를 전부 실행할 권한으로 해석하지 않는다.

시작할 때:

1. 위 세 문서와 대상 디렉터리의 추가 `AGENTS.md`를 읽는다.
2. `git status --short` 및 대상 파일의 `git diff -- <경로>`를 확인한다. Windows 마운트에서는 전체 상태 조회가 느릴 수 있으므로 반복 호출을 줄인다.
3. STATUS의 설정값·파일 존재 여부를 실제 파일과 대조한다. 충돌하면 최신 파일과 사용자 지시를 우선하고 불일치를 기록한다.
4. 이번 요청 범위, 수정 예정 파일, 완료 기준을 STATUS의 진행 중 작업에 적는다. 짧은 수정도 이전 작업과 구분할 수 있게 남긴다.

## 작업 단위

한 세션에서는 메뉴 한 화면, 도감 항목 한 종류 등 검증 가능한 범위로 작업한다. 큰 요청은 중간 완료 지점을 남기면서 계속 진행한다.

| 종류 | 주로 볼 파일 | 확인할 내용 |
| --- | --- | --- |
| 포켓몬 이름·분류 | `src/data/pokemon/species_info/gen_*_families.h` | 폼 간 이름 일관성, 공식 분류, 바이트 길이 |
| 기술명 | `src/data/moves_info.h`, `include/constants/global.h` | 공식 표기, 이름 버퍼와 화면 폭 |
| 메뉴·이름 입력 | `src/option_menu.c`, `src/naming_screen.c`, `src/challenge_menu.c` | 창 좌표, 선택 커서, 입력·삭제·저장, 잘림 |
| 한글 처리 | `charmap.txt`, `src/korean.c`, `src/korean_table.c`, `src/text.c`, `graphics/fonts/` | 지원 글자, 조사, 글리프 폭, 제어 코드 |
| 배틀 그림 | `src/data/graphics/pokemon.h`, `include/graphics.h`, 종 데이터, `graphics/pokemon/` | 앞뒤 그림, 팔레트, 프레임 범위, 위치·그림자 |

명칭을 새로 조사할 때는 확인한 출처 URL·확인 날짜·예외를 SESSION_LOG에 남긴다. 과거 작업에서 사용한 PokeAPI 한국어 데이터는 보조 자료이며, 공식 한국어 자료와 불일치하면 공식 자료를 확인한다. 영문 자동 치환만으로 번역 완료를 판정하지 않는다.

문자열의 `{...}` 치환 토큰, `\n` 등 줄 제어, 문자열 종료 방식은 유지한다. UTF-8 소스의 글자 수와 게임 인코딩의 바이트 수는 다르다. 버퍼 길이와 저장 데이터 구조를 변경할 때는 사용하는 코드와 세이브 영향까지 확인한다.

## 검증과 빌드

1. 대상 파일 diff를 확인해 요청 외 데이터가 변경되지 않았는지 검사한다.
2. `git diff --check -- <수정한 파일들>`로 공백 오류를 확인한다. 새 파일은 별도로 내용을 점검한다.
3. 변경과 관련된 인코딩·누락·그래픽 참조 검사를 수행한다. 문서만 수정한 경우 ROM 재빌드는 필요 없다.
4. 코드·문자열·그림 변경을 전달할 때 HNS를 빌드하고 종료 코드와 로그를 확인한다.

WSL/bash 빌드 예시(로그는 저장소 안에 보관):

```bash
mkdir -p build/localization-logs
build_log="build/localization-logs/hns-$(date +%Y%m%d-%H%M%S).log"
make hns -j8 > "$build_log" 2>&1
build_result=$?
tail -n 25 "$build_log"
printf 'Build exit code: %s\nLog: %s\n' "$build_result" "$build_log"
```

종 데이터 의존성 검사와 컴파일은 수분 걸릴 수 있다. 출력이 없다는 이유만으로 빌드를 중복 실행하지 않는다. 이전 세션 빌드가 남아 있다면 프로세스·로그 상태부터 확인한다. 세션 ID는 다른 세션에서 재사용된다고 가정하지 않는다.

성공 판정은 종료 코드 0, 최종 링크 결과, 갱신된 `pokehns.gba`로 한다. 예전 ROM이 남아 있을 수 있으므로 파일 존재만으로 성공이라고 하지 않는다. 메모리 사용량도 기록한다. 2026-09-11 기준 ROM 여유는 약 291KiB로 적다. 실제 표시 검증을 못 했다면 그 사실과 재현 절차를 남긴다.

검증할 화면 예시:

- 메뉴: 진입·커서 이동·값 변경·복귀 후 저장, 가장 긴 한글 항목의 잘림.
- 이름: 니드런 성별, 긴 이름, 이름 입력·삭제, 전투·도감·상태창 표시.
- 그림: 싱글/더블 배틀, 앞뒤·이로치·성별 차이, 등장 애니메이션, 그림자, 메가진화.

새 변경이나 오류가 없다면 성공한 전체 빌드를 반복하지 않는다.

## 세션 종료와 갑작스러운 중단 대비

파일 수정 완료, 검증 완료, 빌드 시작/종료처럼 의미 있는 지점마다 STATUS를 갱신한다. 마지막 답변에만 진행 상황을 남기지 않는다.

- STATUS: 현재 진행 중인 일, 완료/미검증 구분, 다음 한 단계, 알려진 오류, 로그 위치.
- SESSION_LOG: 날짜, 요청, 이번에 수정한 경로, 결정 이유, 검증 명령과 결과, 남은 일.
- 중요한 빌드 결과는 `docs/localization/evidence/`에 짧은 로그를 보관한다. 대량 중간 산출물은 `build/`에 둔다.
- `/tmp`의 자료·백업은 사라질 수 있다. 다시 필요할 자료는 출처와 재생성 방법을 기록하거나 필요한 부분만 저장소에 보존한다.
- 복잡한 수정 전에는 대상 파일의 기존 diff와 미추적 원본을 별도 백업할 수 있다. Git의 HEAD에는 미커밋 사용자 수정이 없으므로 HEAD를 작업 전 백업으로 간주하지 않는다.
- Git 커밋을 만드는 작업에서는 요청 범위의 파일과 필요한 새 PNG/PAL을 명시적으로 선택한다. 다른 변경까지 묶지 않는다. 원격 push·배포는 별도 요청 범위에 따라 수행한다.

같은 폴더의 다음 세션은 미커밋 파일도 읽을 수 있다. 다른 PC나 새 clone으로 옮길 때는 문서만이 아니라 실제 수정 파일과 미추적 그림 파일도 함께 전달해야 한다. 문서는 코드 백업을 대신하지 않는다.

## 세션 기록 템플릿

아래 내용을 SESSION_LOG 끝에 추가한다. STATUS에는 최신 상태만 유지한다.

```markdown
### YYYY-MM-DD — 작업 제목
- 요청/범위:
- 수정 파일:
- 변경과 결정 이유:
- 출처(새 명칭 조사 시 URL·확인일):
- 검증: 명령, 종료 코드, 결과, 로그 위치
- 게임 화면 확인: 완료한 화면 / 미확인 항목
- 남은 문제:
- 다음 시작점: 파일·함수 또는 실행할 명령
```
